# GameStats CS2 — SIS1

Программа анализирует результаты матчей CS2 одного игрока. Одна задача — одна игровая сессия из JSON-файла. Пользователь переносит показатели из итоговой таблицы матчей, программа рассчитывает общий отчёт.

Требуется **Go 1.27.x**. Используется только стандартная библиотека. Все Go-файлы находятся в одном `package main`.

## Запуск

Команды выполнять из папки `sis1`:

```bash
go version
go run . examples/session.json
go run . examples/session.json examples/draw.json
```

Несколько файлов обрабатываются в одном процессе: каждому соответствует отдельная задача с ID 1, 2 и далее в порядке аргументов. Задачи и отчёты хранятся в памяти только до завершения процесса; при новом запуске ID снова начинаются с 1.

Пример первого отчёта:

```text
Task: 1
Status: completed
Matches: 3
Wins: 2
Losses: 1
Draws: 0
Total kills: 48
Total deaths: 36
Total assists: 18
Win rate: 66.67%
Average kills: 16.00
Average deaths: 12.00
Average assists: 6.00
```

## Данные и правила

Файл содержит непустой массив матчей одной сессии одного игрока:

```json
[
  {"result": "win", "kills": 18, "deaths": 12, "assists": 6},
  {"result": "loss", "kills": 10, "deaths": 16, "assists": 4}
]
```

Все четыре поля обязательны. `result` принимает `win`, `loss` или `draw`; остальные поля — целые числа не меньше нуля. Ноль допустим, пропуск поля или `null` — ошибка. Неизвестные поля, дробные числа, некорректный JSON и второй документ после массива отклоняются.

Процент побед: `wins / match_count * 100` с преобразованием в `float64`. Ничьи входят в общее количество матчей. Средние убийства, смерти и помощь — соответствующая сумма, делённая на число матчей. На количество смертей программа не делит, поэтому ноль смертей допустим.

Результаты хранятся без округления. При печати процент и средние показываются с двумя знаками после точки. Переполнение целочисленной суммы возвращает ошибку.

## Задачи и состояния

`Task` содержит уникальный в пределах запуска ID, входные матчи, статус и результат. `TaskStore` хранит задачи в `map[int]Task`.

| Операция | Поведение |
|---|---|
| `Create(matches)` | Проверяет ввод, копирует матчи, создаёт `pending` |
| `Get(id)` | Возвращает копию задачи; неизвестный ID даёт ошибку |
| `Process(id)` | Выполняет расчёт, сохраняет результат и новое состояние |

Разрешённые переходы:

```text
pending → processing → completed
                     → failed
```

`processing` устанавливается до расчётов. Ошибка расчёта переводит задачу в `failed`; например, если сумма показателей не помещается в `int`. `completed` и `failed` терминальны: повторная обработка запрещена. Обрабатывать уже находящуюся в `processing` задачу тоже нельзя.

У `pending`, `processing`, `failed` результат остаётся нулевой структурой; готовым отчётом он считается только при `completed`. Печатать незавершённую задачу нельзя. Изменение переданного среза или полученной копии задачи не меняет сохранённые данные.

Обычные ошибки возвращаются через `error`. CLI пишет их в stderr с контекстом файла и завершает работу с ненулевым кодом. Отчёты печатаются после успешной обработки всех входов, поэтому неверный второй файл не оставляет в stdout отчёт только по первому.

## Как читать код и объяснять его на защите

1. `stats.go`: структуры `Match`, `Report`; проверка входа; цикл `for range`, `switch`, суммы и средние.
2. `tasks.go`: структура `Task`, map, ID и методы создания/получения/обработки.
3. `json.go`: перевод JSON в срез матчей.
4. `main.go`: открытие файлов, вызовы методов и печать.

Связь с загруженными лекциями:

| Материал | Что используется |
|---|---|
| Week 2, стр. 2–3 | `[]Match`, `append`, `make` и `copy` |
| Week 3, стр. 8–10 | Запись в map, поиск `task, ok := s.tasks[id]` |
| Week 4, стр. 1 и 10 | Структуры по примеру Student, pointer receiver по примеру Counter |
| Week 5, стр. 5 | `writeReport(w io.Writer, ...)`, `os.Stdout`, `strings.Builder` |

При копировании структуры срез всё ещё ссылается на общий массив. Поэтому `copyTask` делает отдельный срез через `make` и `copy`. Сам `Report` содержит только числа и копируется вместе со структурой.

Pointer receiver, например `(t *Task) start()`, позволяет изменить исходный статус. При изменении элемента map сначала получается значение задачи, затем изменённая структура записывается обратно по тому же ключу.

Интерфейс `io.Writer` задаёт метод записи. Одна функция `writeReport` работает и с терминалом (`os.Stdout`), и со строкой (`*strings.Builder`) в тестах. Это содержательное использование интерфейса по примеру лекции; отдельный пользовательский интерфейс не нужен.

JSON и unit-тесты добавлены через стандартные `encoding/json` и `testing`. Указатели в закрытой структуре `matchInput` нужны, чтобы различать пропущенное поле и значение 0. После проверки данные преобразуются в обычный `Match` с полями `int`.

## Проверки SIS1

```bash
gofmt -l .
go build ./...
go vet ./...
go test ./...
```

`gofmt -l .` не должен вывести ни одного файла. В тестах есть все девять обязательных категорий: создание, неверный ввод, получение, неизвестный ID, обработка, правильный результат, состояние после обработки, недопустимая операция и независимые задачи. В нескольких тестах используются таблицы случаев и `t.Run`.

Пример ошибочного запуска:

```bash
go run . examples/does-not-exist.json
```

Для защиты можно показать два корректных файла, затем пример ошибки и `go test -v ./...`. Тесты также демонстрируют запрет повторной обработки, переход в `failed` и независимость входов/результатов.
