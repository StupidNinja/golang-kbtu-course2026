# GameStats CS2: спецификация SIS1

Дата: 2026-10-18. Основание: [требования преподавателя](../../requirements/SIS_CP1_SPECIFICATION.md) и обсуждение проекта с пользователем.

## Цель и учебный уровень

Приложение на Go анализирует результаты матчей CS2 одного игрока. Пользователь выбрал небольшой проект для уверенной защиты и ручное заполнение JSON.

Дополнительное требование пользователя: писать максимально просто, как студент, который только изучает Go, опираясь на примеры из загруженных лекций. Код должен быть понятен построчно: обычные структуры, циклы, условия, методы, map, срезы и явные проверки ошибок. Привязка к конкретным страницам лекций приведена в [плане](../plans/2026-10-18-gamestats-cs2.md).

Один JSON-файл описывает одну сессию и создаёт одну задачу. Несколько файлов обрабатываются последовательно в одном процессе. Матчи одной сессии относятся к одному игроку; это обеспечивает пользователь.

Задачи и результаты хранятся только в памяти. HTTP, конкурентность и внешние API относятся к дальнейшим этапам согласно заданию.

## Входные данные

Корень файла — непустой массив. Все четыре поля каждого матча обязательны:

```json
[
  {"result": "win", "kills": 18, "deaths": 12, "assists": 6},
  {"result": "loss", "kills": 10, "deaths": 16, "assists": 4},
  {"result": "win", "kills": 20, "deaths": 8, "assists": 8}
]
```

- `result`: `win`, `loss` или `draw`, с учётом регистра.
- Остальные поля: целые числа Go `int`, не меньше нуля. Ноль допустим.
- Пустой файл, пустой массив, корневой `null`, объект вместо массива, пропущенные поля и `null` вместо полей отклоняются.
- Дробные числа, числа вне диапазона `int`, неизвестные поля и второй JSON-документ после массива отклоняются. Пробелы после массива разрешены.
- При создании задачи из Go выполняются те же доменные проверки.
- Произвольных игровых ограничений нет. Переполнение суммы возвращает ошибку при анализе; для проверки используется понятное сравнение с `math.MaxInt` перед сложением.

Для JSON нужна небольшая закрытая структура с `*string` и `*int`: она позволяет отличить пропущенное поле от настоящего нуля. Это локальная деталь чтения; в `Match` остаются обычные значения. Используются `json.Decoder`, `DisallowUnknownFields` и проверка `io.EOF` после первого документа.

## Расчёты

Отчёт содержит количество матчей, побед, поражений и ничьих; суммы убийств, смертей и помощи; процент побед; средние убийства, смерти и помощь за матч.

- `match_count = wins + losses + draws`.
- `win_rate = float64(wins) / float64(match_count) * 100`: ничьи входят в знаменатель.
- Каждое среднее — соответствующая сумма, делённая на число матчей. Деления на смерти нет.
- Значения сохраняются без округления. При печати процент и средние выводятся с двумя знаками после точки; в тестах допуск `1e-9`.

Контрольный пример выше: 3 матча, 2 победы, 1 поражение, 0 ничьих; суммы 48/36/18; средние 16/12/6; процент побед `200.0 / 3.0`. Один `draw` с нулями: 1 матч, 1 ничья, остальные показатели 0.

## Простая структура программы

В существующей папке `sis1` создаётся один модуль `gamestats`, `go 1.27.0`. Все Go-файлы относятся к одному `package main`:

- `stats.go`: Match, Report, проверка матчей и обычная функция расчётов.
- `tasks.go`: Task, TaskStore, состояния и работа с map.
- `json.go`: чтение JSON из `io.Reader`.
- `main.go`: аргументы, открытие файлов, последовательные вызовы и печать.

Используется только стандартная библиотека. Отдельная библиотека и каталог cmd не нужны для этого объёма.

```go
type Match struct {
    Result  string `json:"result"`
    Kills   int    `json:"kills"`
    Deaths  int    `json:"deaths"`
    Assists int    `json:"assists"`
}

type Report struct {
    MatchCount     int
    Wins           int
    Losses         int
    Draws          int
    TotalKills     int
    TotalDeaths    int
    TotalAssists   int
    WinRate        float64
    AverageKills   float64
    AverageDeaths  float64
    AverageAssists float64
}

type Task struct {
    ID     int
    Input  []Match
    Status string
    Result Report
}

type TaskStore struct {
    tasks  map[int]Task
    nextID int
}

func validateMatches(matches []Match) error
func AnalyzeMatches(matches []Match) (Report, error)
func NewTaskStore() *TaskStore
func (s *TaskStore) Create(matches []Match) (Task, error)
func (s *TaskStore) Get(id int) (Task, error)
func (s *TaskStore) Process(id int) (Task, error)
func (t *Task) start() error
func copyTask(task Task) Task
func DecodeSession(r io.Reader) ([]Match, error)
func run(paths []string, out io.Writer) error
func writeReport(w io.Writer, task Task) error
```

Имена строковых констант: `ResultWin="win"`, `ResultLoss="loss"`, `ResultDraw="draw"`; `StatusPending="pending"`, `StatusProcessing="processing"`, `StatusCompleted="completed"`, `StatusFailed="failed"`.

`NewTaskStore` создаёт map через `make` и устанавливает следующий ID в 1. Поиск использует `task, ok := s.tasks[id]`. Методы, которые меняют хранилище или задачу, используют pointer receiver по примеру Counter из Week 4.

Содержательный интерфейс — `io.Writer` в `writeReport`, ровно по примеру Week 5, стр. 5: в программе используется `os.Stdout`, в тесте `*strings.Builder`. ТЗ не требует объявлять собственный интерфейс. Отдельные Analyzer, подмена обработчиков и callback-функции не нужны.

Ошибки возвращаются через обычные `errors.New` или `fmt.Errorf`, проверяются `if err != nil`. Специальных типов ошибок и цепочек из нескольких обёрток нет. Сообщения поясняют файл или неверный матч; обычные ошибки не вызывают panic.

## Состояния и независимость задач

- `Create` проверяет ввод, копирует матчи, выдаёт ID, сохраняет `pending`. Неверный ввод не создаёт задачу и не расходует ID.
- `start` разрешён только из `pending` и меняет задачу на `processing`. Он используется внутри Process и прямо проверяется отдельным простым тестом.
- `Process` получает задачу из map, вызывает start, сохраняет processing до расчёта и вызывает AnalyzeMatches. Успех сохраняет Report и `completed`; ошибка расчёта сохраняет `failed` и возвращается вызывающему коду.
- `completed` и `failed` — терминальные состояния: повторная обработка возвращает ошибку. Неизвестный ID также возвращает ошибку.
- До завершения Result — нулевая структура; готовым отчётом она считается только при `completed`. При failed сохраняется нулевой Report. Печать незавершённой задачи возвращает ошибку.
- Task и Report копируются как обычные структуры. Для Input функция copyTask использует `make` и `copy`, как Week 2, стр. 3. Create копирует исходный ввод, а Create/Get/Process возвращают копии. Изменение переданного среза или возвращённой задачи не меняет сохранённые данные.

Дополнительное состояние failed нужно для реальной ошибки переполнения сумм. Искусственные анализаторы и ошибки ради тестов не вводятся.

## Запуск и отчёт

Из папки `sis1`:

```bash
go run . examples/session.json examples/draw.json
```

Один процесс создаёт один TaskStore, последовательно открывает каждый файл, читает JSON и вызывает Create → Process → Get. Файл закрывается после чтения. Завершённые задачи собираются в срез в порядке аргументов, затем печатаются через writeReport. Отдельный процесс на каждый файл потерял бы задачи в памяти.

Формат одного отчёта:

```text
Task: 1
Status: completed
Matches: 3
Wins: 2
Losses: 1
Draws: 0
Total kills: 48
Total deaths: 36
Total assists: 18
Win rate: 66.67%
Average kills: 16.00
Average deaths: 12.00
Average assists: 6.00
```

После каждого отчёта печатается пустая строка. Отсутствие аргументов — ошибка использования. Ошибка файла/ввода/обработки останавливает запуск с понятным сообщением в stderr и ненулевым кодом; до обработки всех входов stdout не заполняется. Ошибки записи отчёта тоже возвращаются.
